# Data Organization Guide

## 🎯 Purpose

This directory demonstrates **proper data organization** for Data Science projects. Understanding the difference between raw, processed, and output data is critical for maintaining data integrity, reproducibility, and professional standards.

---

## 📁 Directory Structure

```
data/
├── raw/                    # Original, immutable source data
├── processed/              # Cleaned and transformed datasets
└── external/               # Third-party or reference data
```

---

## 🔒 RAW DATA (`raw/`)

### Purpose
Store original, unmodified data exactly as received from the source.

### Golden Rules
- ✅ **NEVER modify files in this folder**
- ✅ Treat as **read-only**
- ✅ Preserve data integrity at all costs
- ✅ Keep original filenames when possible

### Why This Matters
Raw data is your **evidence**. If you modify it:
- You lose the ability to verify your analysis
- You can't reproduce results from scratch
- You break the audit trail
- You risk data corruption

### Current Files
- `energy_usage_sample.csv` - Original energy consumption data (2026-02-01)

### Best Practices
```python
# ✓ CORRECT: Read raw data without modifying
df = pd.read_csv('data/raw/energy_usage_sample.csv')

# ✗ WRONG: Never save back to raw folder
df.to_csv('data/raw/energy_usage_sample.csv')  # DON'T DO THIS!
```

---

## 🔄 PROCESSED DATA (`processed/`)

### Purpose
Store cleaned, transformed, and analysis-ready datasets derived from raw data.

### When to Use
- After removing duplicates
- After handling missing values
- After feature engineering
- After data normalization
- After filtering or subsetting

### Naming Convention
Use descriptive names that indicate the processing applied:
- `energy_usage_cleaned.csv` (duplicates removed, types corrected)
- `energy_daily_aggregates.csv` (aggregated to daily level)
- `energy_features_engineered.csv` (with derived features)

### Current Files
- `energy_usage_cleaned.csv` - Cleaned data with hour extraction and peak indicators

### Best Practices
```python
# ✓ CORRECT: Read from raw, save to processed
df_raw = pd.read_csv('data/raw/energy_usage_sample.csv')
df_clean = clean_data(df_raw)  # Apply transformations
df_clean.to_csv('data/processed/energy_usage_cleaned.csv', index=False)

# ✓ CORRECT: Processed data can be recreated anytime
# If you lose processed data, just re-run your cleaning script
```

### Documentation Requirement
For each processed file, document:
- Source raw file(s)
- Transformations applied
- Date processed
- Script used for processing

---

## 🌍 EXTERNAL DATA (`external/`)

### Purpose
Store third-party datasets, reference data, or supplementary information not generated by your project.

### Examples
- Weather data from external APIs
- Public holiday calendars
- Geographic reference files
- Industry benchmarks

### Why Separate?
- Clearly distinguishes your data from external sources
- Makes dependencies explicit
- Helps with data provenance tracking

---

## ⚠️ DATA CONTAMINATION RISKS

### Problem: Overwriting Raw Data
```python
# ✗ DANGER: This overwrites your original evidence
df = pd.read_csv('data/raw/original.csv')
df = df.dropna()  # Clean the data
df.to_csv('data/raw/original.csv')  # WRONG! Original is gone forever
```

**Impact:** You can never verify if your cleaning was correct.

### Solution: Clear Separation
```python
# ✓ SAFE: Raw data remains intact
df_raw = pd.read_csv('data/raw/original.csv')
df_clean = df_raw.dropna()  # Clean the data
df_clean.to_csv('data/processed/original_cleaned.csv')  # Save separately
```

**Benefit:** You can always go back to the source.

## 🔄 ONE-DIRECTIONAL DATA FLOW

### The Correct Workflow

```
RAW DATA (read-only)
    ↓ (read)
PROCESSING SCRIPT
    ↓ (write)
PROCESSED DATA
    ↓ (read)
ANALYSIS/MODELING
    ↓ (write)
OUTPUTS (figures, reports, models)
```

### Key Principle
**Data flows in ONE direction:** Raw → Processed → Outputs

**Never:**
- Read from processed and write to raw
- Mix output files with input data
- Create circular dependencies

---

## 📊 OUTPUTS ARE NOT DATA

### Important Distinction
Outputs (plots, reports, models) belong in the `outputs/` directory, **NOT** in `data/`.

**Why?**
- Outputs are generated artifacts, not source material
- They can be recreated from data
- Mixing them confuses the pipeline

```
data/              # Input to analysis
outputs/           # Results of analysis
```

---

## ✅ VERIFICATION CHECKLIST

Before considering your data organization complete:

- [ ] Raw data is in `data/raw/` and unmodified
- [ ] Processed data is in `data/processed/` with descriptive names
- [ ] External data (if any) is in `data/external/`
- [ ] No output files are mixed with data files
- [ ] Processing scripts read from raw, write to processed
- [ ] You can delete processed data and recreate it from raw
- [ ] Data flow is one-directional (no circular dependencies)

## 🚨 Common Mistakes to Avoid

| Mistake | Why It's Bad | Correct Approach |
|---------|--------------|------------------|
| Editing raw files directly | Loses original evidence | Always work on copies |
| Saving outputs in data/ | Confuses inputs and results | Use outputs/ folder |
| No documentation of processing | Can't reproduce results | Document transformations |
| Unclear file naming | Hard to track lineage | Use descriptive names |
| Mixing data stages | Breaks workflow clarity | Separate raw/processed/output |
